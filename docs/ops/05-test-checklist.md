# 배포 후 실환경 E2E 테스트 체크리스트

## 이 체크리스트가 필요한 이유

`node scripts/check-web.mjs`, `node scripts/test-gas-actions.mjs`(모의 SpreadsheetApp 기반)는 로직과 스키마를 검증하지만, 아래 세 가지는 **실제 배포 환경에서만** 확인할 수 있다:

1. 실제 Google `tokeninfo` 엔드포인트로의 토큰 검증(aud/iss/exp/email_verified) — 모의 테스트는 이 부분을 가짜 응답으로 대체하고 있다.
2. 실제 Google Sheets에 대한 읽기/쓰기(권한, 셀 서식, 동시성 잠금) — 모의 테스트는 메모리 상의 가짜 시트를 쓴다.
3. GitHub Pages ↔ GAS 간 실제 네트워크 요청(CORS, `Content-Type: text/plain` 우회가 실제로 preflight를 피하는지) — 모의 테스트는 브라우저 fetch를 거치지 않는다.

배포할 때마다(최초 배포 + 이후 재배포마다) 아래 항목을 순서대로 확인한다. 하나라도 실패하면 해당 항목의 원인을 해결한 뒤 처음부터 다시 확인한다.

## 체크리스트

- [ ] **E1 학생 로그인**: 찬양팀 학생 계정(MEMBERS에 `role=student`, `active` 활성)으로 로그인 → "오늘" 탭 진입, 오늘 날짜와 맥체인 본문이 표시된다.
- [ ] **E2 오늘 기록 저장**: 말씀읽음 체크, 와닿은말씀·결단 텍스트 입력, 수련회기도 체크 후 저장 → 저장 성공 표시(토스트 등) 확인.
- [ ] **E3 시트 반영 확인**: 구글 시트 RECORDS 탭을 열어 오늘 날짜·로그인한 학생의 행이 생성되었는지 확인. 다음을 셀 단위로 대조:
  - `email` 열 = 로그인 토큰의 email과 일치 (학생이 화면에서 입력한 값이 아니라 서버가 채운 값이어야 함)
  - `이름` 열 = MEMBERS에 등록된 이름과 일치
  - `말씀읽음`, `수련회기도` 열 = 문자열 `TRUE`/`FALSE` (boolean이 아니라 정확히 이 문자열 형식)
  - `와닿은말씀`, `결단` 열 = 화면에 입력한 텍스트 그대로
  - `기록시각`, `수정시각` 열 = ISO 형식 시각 값, 최초 저장이므로 두 값이 같거나 근접
- [ ] **E4 수정 후 재저장 — 행 갱신 확인**: 같은 날 와닿은말씀 텍스트를 바꿔서 다시 저장 → RECORDS 탭에서 **같은 (날짜, email) 행이 1개만 유지**되고 내용이 갱신되었는지 확인 (새 행이 추가되면 안 됨 — upsert 실패). `수정시각`이 갱신되고 `기록시각`은 최초 값 그대로인지 확인.
- [ ] **E5 나의 현황 반영**: "나의 현황" 탭으로 이동 → streak, 이번 주/이번 달 달성률, 최근 기록 리스트에 방금 저장한 기록이 반영되어 있는지 확인. 저장 직후 캐시(TTL 2분) 때문에 반영이 안 보이면 새로고침 후 재확인(무효화가 정상 동작하면 새로고침 없이도 즉시 반영되어야 한다).
- [ ] **E6 교사 로그인**: 교사 계정(`role=teacher` 또는 `admin`)으로 로그인 → "우리팀" 탭이 보이는지 확인(학생 계정에는 이 탭이 보이지 않아야 함).
- [ ] **E7 우리팀 조회**: "우리팀" 탭에서 활성 학생 전원의 최근 7일 기록 그리드(○/×)와 streak/달성률 요약이 표시되는지 확인. 방금 E2~E4에서 기록한 학생의 데이터가 정확히 반영되는지 대조.
- [ ] **E8 학생 접근 제한 확인**: 학생 계정으로 로그인한 상태에서 브라우저 개발자 도구 콘솔에 다음을 입력해 다른 사람 기록에 접근이 막히는지 확인:
  ```js
  fetch(GAS_URL, {
    method: 'POST',
    headers: { 'Content-Type': 'text/plain' },
    body: JSON.stringify({ action: 'getAllRecords', idToken: sessionStorage.idToken })
  }).then(r => r.json()).then(console.log)
  ```
  기대 결과: `{"ok":false,"code":"forbidden"}` (학생은 `getAllRecords`, `getMembers` 액션을 호출할 권한이 없다).
- [ ] **E9 미등록/비활성 계정 차단**: MEMBERS에 없는 이메일 또는 `active`가 비활성인 이메일로 로그인 시도 → 접근 권한 없음 화면(`unauthorized`) 확인.
- [ ] **E10 날짜 범위 제한**: "오늘" 탭에서 어제 기록으로 전환해 저장이 되는지 확인(정상 허용). 브라우저 콘솔에서 내일 날짜로 `setRecord`를 직접 호출해 `{"ok":false,"code":"bad_request"}`가 반환되는지 확인(오늘·어제 외 날짜는 거부되어야 한다).
- [ ] **E11 기록 안 한 경우 독려 메시지**: 새 학생 계정(또는 최근 며칠 기록이 없는 계정)으로 로그인 → "나의 현황" 탭에 독려 메시지 배너가 표시되는지 확인.

## 자가 등록 시나리오 (v1.1, 계약 §7)

- [ ] **E12 미등록 계정 → 가입 화면 표시**: MEMBERS에 없는 신규 이메일로 로그인 → (`REGISTER_CODE`가 설정되어 있어 `canRegister=true`인 경우) `unauthorized` 안내 화면이 아니라 가입 화면(RegisterScreen)이 표시되는지 확인. 로그인 email이 화면에 표시되고, 이름(필수)·파트(선택)·등록 코드 입력란이 보이는지 확인.
- [ ] **E13 잘못된 코드 거부**: 가입 화면에서 등록 코드를 일부러 틀리게 입력하고 등록 시도 → `bad_code` 에러로 거부되고 화면에 안내 문구가 표시되는지 확인(MEMBERS에 행이 생성되지 않아야 함).
- [ ] **E14 올바른 코드로 가입**: 팀에 공지된 올바른 등록 코드로 다시 등록 시도 → 등록 성공 확인. MEMBERS 시트에 새 행이 생성되었는지 셀 단위로 대조: `email`=로그인 토큰의 email(소문자), `role`=`student`, `active`=`TRUE`, `이름`=화면에 입력한 값.
- [ ] **E15 가입 직후 즉시 기록 가능**: 등록 성공 응답을 받은 즉시(재로그인 없이) "오늘" 탭으로 진입해 오늘 기록을 저장할 수 있는지 확인.
- [ ] **E16 비활성 계정 재가입 차단**: E14에서 가입한 계정을 MEMBERS에서 `active=FALSE`로 바꾼 뒤, 같은 이메일로 다시 가입 시도 → `deactivated` 에러로 거부되고 `active`가 자동으로 `TRUE`로 되돌아가지 않는지 확인(재활성화는 교사가 시트에서 직접 처리해야 함).

## 참고
- 위 항목 중 E3, E4, E10은 실제 시트 쓰기와 실제 날짜 검증 로직을 함께 확인하므로 배포 후 반드시 직접 실행해야 한다. 모의 테스트 스크립트로는 "돌아갈 것"이라고 짐작할 수 있을 뿐, 실제 시트에 정확한 형식으로 기록되는지는 이 체크리스트로만 확인 가능하다.
- 실패 항목이 있으면 `06-operations.md`의 "문제 해결" 표에서 에러 코드에 해당하는 원인을 먼저 확인한다.
